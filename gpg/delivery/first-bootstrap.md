# Доставка VM GPG-ключа на ADM (первый бутстрап)

Этот шаг — единственный неавтоматизированный пункт во всей цепочке
disaster recovery. До него VM физически не может расшифровать pass-store,
синхронизированный в S3 — поэтому доставка не может идти через тот же S3
канал (курица и яйцо).

## Шаги

1. Локально: `secrets/gpg/master/issue-vm-key.sh <vm-id>` — выпускает
   приватный ключ под конкретную VM, сохраняет его во временный файл
   (`*.asc`), печатает путь.
2. Доставить файл на ADM защищённым каналом — `scp`/аналог, вручную,
   с текущей машины на `yandex-cloud-adm`. Не класть файл в S3/GitHub ни на
   каком промежуточном шаге.
3. На ADM: импортировать ключ (`gpg --import <file>.asc`), затем удалить
   файл (`shred -u` или `rm -f`) — он не должен оставаться на диске ADM
   после импорта.
4. Прогнать `ansible/roles/gnupg_pass` (входит в `make workspace`) — роль
   проверит, что секретный ключ присутствует, и инициализирует `pass`.
5. Дальше — `make secrets` (этот репозиторий) и `session_open.yml`
   (репозиторий `ansible/`) уже работают через обычный S3-канал.

## Когда повторять

- Пересоздание ADM с нуля (disaster recovery) — повторить целиком.
- Компрометация/утеря VM-ключа конкретной машины — выпустить новый ключ для
  того же `vm-id` и повторить доставку; старый ключ отозвать в `pass`
  (переинициализировать store под новый `.gpg-id`, если требуется полная
  ротация доступа).
